> regenerated by `parse_bench.py` — hand-written conclusions do not belong in generated output.

## Tier 3 — Human veto → **pdfplumber DISQUALIFIED**

Reading the excerpts (PRML p60) exposed damage that **no metric detected**:

```text
1.5.DecisionTheory 41
Figure1.25 An example of a loss matrix with ele- (cid:15)cancer normal(cid:16)
mentsL kj forthecancertreatmentproblem. Therows
correspondtothetrueclass,whereasthecolumnscor-
```

Two failures: **word-boundary collapse** and **raw `(cid:N)` glyph codes** leaking into text.
Confirmed systematic across PRML, Goodfellow and Jurafsky — dozens of 25+ character glued
tokens (`wecanoptimallyencodexjustusingamatrix`,
`ifapatientwhodoesnothavecancerisincorrectlydiagnosed`).

**Why every metric missed it — the important lesson:**

| Metric | Effect | Cause |
|---|---|---|
| `chars_per_page` | invisible | strips whitespace before counting |
| `alpha_ratio` | invisible | the letters are all still there |
| `single_char_token_ratio` | **improved** | gluing words *reduces* single-char tokens |
| `broken_hyphen_rate` | partially caught | flagged ~2× damage, but not the cause |

One metric **actively rewarded the damage**. The proxies ranked pdfplumber third, but for
largely the wrong reasons. Only the human veto caught the real problem.

This is the strongest possible validation of Tier 3, and the strongest possible warning
against a fully automated selection rule on proxy metrics.

> **Follow-up for Phase 2:** add a `word_integrity` metric — e.g. the fraction of alphabetic
> tokens exceeding ~22 characters (essentially nonexistent in real English), or a dictionary
> hit rate. The current metric set has a blind spot and should not be reused as-is.

## Tier 4 — Capability

**`pdfplumber` recovered 0 TOC entries on all six books** (no outline API), so it would have
required a two-parser pipeline even without the veto. `pymupdf`, `pymupdf_sorted` and `pypdf`
all recovered identical counts (109/194/105/166/285/548).

## Tie-break → **`pymupdf`**

Survivors ranked: `pymupdf_sorted` 0.978, `pymupdf` 0.968.

Gap = **1.02%**, inside the pre-registered **3% band**, so this is a statistical tie at n=48.
Rule says prefer the faster parser:

```
pymupdf         66.1 ms/page
pymupdf_sorted  81.8 ms/page     (+24% slower, no measurable quality gain)
```

**Supporting evidence, found after the tie-break and consistent with it:** `pymupdf_sorted`
reports `repeated_line_ratio = 0.000` on *every* book, while plain `pymupdf` detects running
headers (0.040 / 0.030 / 0.023). Per the rule, a suspiciously low value means the parser is
probably *merging* page furniture into body text rather than emitting it cleanly — which would
make Phase 2's header stripping harder, not easier. Plain `pymupdf` keeps headers as separable
lines.

---

## Prior: FALSIFIED

The pre-registered prior was **`pymupdf_sorted` wins**, on the reasoning that multi-column
layouts need `sort=True` for correct reading order.

It scored highest — but by 1.02%, inside the noise band, while costing 24% more time. The
reading-order benefit that motivated the prior did not show up as measurable quality on this
corpus. These are well-structured born-digital publisher PDFs; the content stream is already
close to reading order, so sorting had little to fix.

**Kept as an option in `ALL_PARSERS`** — if Phase 2 cleaning reveals column-interleaving on
specific pages, it is one config value away.

## Secondary finding worth reporting

**`pypdf` — the naive tutorial default — fails catastrophically on the most mathematical book.**

| Book | pypdf single_char | pymupdf single_char |
|---|---|---|
| deeplearningbook | **0.4802** | 0.1663 |

Nearly half of all tokens on Goodfellow pages are single characters under `pypdf` — textbook
equation shatter. It is competitive on prose-heavy books and collapses exactly where the
mathematics lives. Since `PyPDFLoader` is what most RAG tutorials reach for by default, this
quantifies the cost of that default on a technical corpus. **Ships in the README.**
